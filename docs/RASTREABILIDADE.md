# Rastreabilidade Técnica

Revisado em 2026-10-13, na [revisão geral da documentação](archive/plans/2026-10-13-revisao-geral-documentacao.md):
leitura estática do checkout com a cadeia ativa de migrations (`001`–`221`) e
consulta ao catálogo de um Postgres local com essas migrations aplicadas
(`scripts/setup-local-pg.sh`). O projeto Supabase remoto não foi conferido.

Este documento liga cada rota e ação da interface ao componente, hook, serviço,
RPC ou tabela que a executa, e à evidência que sustenta esse caminho
([ADR 0082](adr/0082-governanca-documental-dono-unico-e-adr-historica.md)). A
regra de negócio fica no módulo dono, linkado em cada linha; o motivo de cada
decisão fica na ADR. Quando uma linha menciona uma regra, é só para orientar a
leitura do caminho.

## Como ler

- **Definição vigente** é a última migration da cadeia ativa
  (`supabase/migrations/`) que cria ou redefine o objeto. Número sem
  qualificação é dessa cadeia. Número da cadeia anterior à consolidação
  ([ADR 0062](adr/0062-consolidacao-migrations-schema-1-0.md)) aparece como
  "migration arquivada `NNN`": os números se repetem nas duas cadeias com
  conteúdos diferentes.
- Testes `*Migration.test.ts` que leem um arquivo inexistente na cadeia ativa
  passam porque `src/test/setup.ts` redireciona a leitura para
  `supabase/migrations_archive/`. Eles provam o texto da cadeia anterior, não o
  comportamento atual, e aparecem aqui só como contrato histórico.
- As colunas **Execução** e **Acesso conferido** das tabelas de contratos vêm
  do catálogo do Postgres local (`SECURITY DEFINER`/`INVOKER` e papéis com
  `EXECUTE`) e da guarda encontrada na definição vigente ou no núcleo que ela
  chama (`_impl`, `_core`, `_legacy_…`). Elas não provam o projeto remoto.
- Quando o código ainda diverge de uma regra decidida, a linha descreve o que
  o código faz hoje e cita a correção pendente no
  [plano de correções](archive/plans/2026-10-14-correcoes-decididas-na-revisao-geral.md) (decisões na
  [ADR 0083](adr/0083-decisoes-da-revisao-geral-da-documentacao.md) e na
  [ADR 0085](adr/0085-modelo-de-permissoes-por-perfil.md), cuja matriz de quem faz o quê está em
  [Segurança](operations/seguranca.md#modelo-de-permissões-por-perfil)). Em 2026-10-14 as linhas
  de permissão ganharam o item P correspondente. Neste arquivo, "(P*n*)" é sempre o item do plano,
  nunca as faixas P1 e P2 da Demurrage.
- Notas de entrega e verificações datadas ficam no arquivo histórico:
  [notas retiradas em 2026-10-13](archive/reports/2026-10-13-notas-retiradas-da-rastreabilidade.md)
  e [notas de 2026-09-19](archive/reports/2026-09-19-notas-historicas-rastreabilidade.md).

## Evidência

- **Código**: caminho confirmado por leitura do código executável (frontend,
  Edge Functions ou SQL das migrations ativas).
- **Teste**: asserção automatizada identificada pelo arquivo. "Teste local-pg"
  é uma suíte `*.local-pg.test.ts` que executa SQL num Postgres local com as
  migrations ativas e shims do Supabase; não prova Auth, PostgREST nem o
  projeto remoto.
- **Teste de contrato SQL**: inspeção textual de migration; prova a forma do
  SQL, não a execução nem a RLS.
- **Runtime**: comportamento observado num ambiente identificado, com data.
- **Suspeita**: hipótese ainda não verificada; a linha diz o que falta.

## Contratos Supabase

### Fronteira de execução

```mermaid
flowchart LR
    Internal["Internal Auth<br/>sessão interna"]
    Portal["Portal Auth<br/>sessão isolada"]
    Edge["Edge Functions<br/>JWT/segredo + service role"]
    API["PostgREST / RPC<br/>schema public exposto"]
    Boundary["RLS + funções<br/>invoker / definer + grants"]
    Data["Tabelas"]
    Indirect["Triggers + jobs<br/>efeitos indiretos"]
    External["MillionSend / Auth Admin / Itaú"]

    Internal --> API
    Portal --> API
    Edge -->|service role| API
    API --> Boundary
    Boundary --> Data
    Data --> Indirect
    Indirect -. pg_net .-> Edge
    Edge --> External
```

`SECURITY INVOKER` continua sujeito a grants e RLS de quem chama.
`SECURITY DEFINER` atravessa a RLS e por isso depende de `search_path`
controlado, de checagem interna de identidade e papel e de ACL explícita. No
catálogo do Postgres local, todas as funções `SECURITY DEFINER` chamadas pelo
app têm `search_path` fixo (`public, pg_temp`, às vezes com `pg_catalog` à
frente). O
default de `EXECUTE` em funções novas nasce fechado na cadeia ativa (cabeçalho
da `001`, ADR 0047); tabelas seguem os grants da plataforma e a fronteira real
é a RLS. Nenhuma RPC tem `EXECUTE` para `anon`: `portal_ship_schedule`
deixou de ter na migration `320` ([ADR 0090](adr/0090-programacao-de-navios-so-com-sessao.md)). A exceção pré-auth de `portal_resolve_login` da ADR 0013
acabou: a migration arquivada `182` revogou seus grants públicos e a ADR 0047
(migration arquivada `297`) encerrou a exceção; na cadeia ativa a função existe
na `002` sem `EXECUTE` para nenhum papel da API. A regra de segurança é de
[Segurança](operations/seguranca.md).

### RPCs chamadas pelo app

Inventário das funções chamadas por `src/` (fora de testes) e por
`supabase/functions/`, incluindo as variantes despachadas por
`portalRpcContracts.ts`. **Código:** extração de `.rpc('…')`, dos auxiliares
`callPortalRpc`, `internalRpc`, `callPixRpc` e `resolveActorNames` e do mapa de
`portalRpcContracts.ts`; `npm run rpc:check` confere no Postgres local que todos
os nomes chamados existem. Chamadores sem prefixo estão em `src/services/`.
"Acesso conferido" descreve a guarda da definição vigente (ou do núcleo que ela
chama); "só pelo grant" indica função sem guarda própria cujo `EXECUTE` é só de
`service_role`.
